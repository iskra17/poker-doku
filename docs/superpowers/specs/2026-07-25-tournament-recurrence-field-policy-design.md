# 토너먼트 반복·인원 정책 개선 설계

## 1. 목표

운영 백오피스의 반복 토너먼트가 짧은 주기로 과도하게 생성·노출되는 문제를 막고,
반복 일정의 종료 경계를 명시한다. 운영자가 최소·최대 참가 인원을 유연하게 설정할 수
있도록 하며, 2~5인 소규모 토너먼트도 일관된 단일 테이블 진행과 상금 정산을 지원한다.

이번 과다 생성 건은 영구 삭제하지 않는다. 반복 템플릿을 비활성화하고 시작 전 회차를
정상 취소 경로로 종결해 로비에서는 제거하되, 템플릿·회차·운영 감사·경제 처리 기록은
보존한다.

## 2. 확정 정책

### 2.1 반복 일정

- 반복은 `매시간`, `매일`, `매주`를 유지한다.
- 반복을 선택하면 첫 회차 시작 일시와 반복 종료 일시가 모두 필수다.
- 첫 회차 시작 일시보다 반복 종료 일시가 앞서면 저장을 거절한다.
- 반복 종료 일시는 포함 경계다. 회차 시작 시각이 종료 일시와 같거나 이르면 생성할 수
  있고, 종료 일시보다 늦으면 생성하지 않는다.
- 템플릿별로 미래의 비종결 회차를 최대 5개만 영속한다.
- 회차가 완료 또는 취소되면 스케줄러가 종료 경계 안의 다음 회차를 채워, 최대 5개의
  순환 창을 유지한다.
- 운영자가 취소한 회차의 occurrence tombstone은 재생성하지 않는다.
- 템플릿 비활성화는 새 회차 생성을 중지한다. 이미 생성된 회차는 별도 취소 없이는
  변경하지 않는 기존 원칙을 유지한다.

### 2.2 로비 노출

- `visibleAt`에 도달한 공개 가능 회차만 로비 후보가 된다.
- 같은 반복 템플릿의 후보는 시작 시각이 빠른 순서로 최대 5개만 노출한다.
- 단발성 토너먼트는 반복 템플릿별 5개 제한에 포함하지 않는다.
- 사용자가 이미 등록했거나 좌석을 보유한 회차는 개인화 목록에서 숨기지 않는다. 일반
  상한 밖이라도 해당 사용자에게 추가로 포함한다.
- 완료·취소 회차의 기존 10분 결과 표시 및 숨김 정책은 유지한다.

이중 제한을 둔다. 스케줄러의 5회 창은 DB 과잉 생성을 막고, 공개 projection의 5개 제한은
기존 데이터나 전환기 데이터가 로비 피로도를 높이지 않도록 방어한다.

### 2.3 리드 용어와 도움말

입력 라벨 옆에 항상 접근 가능한 도움말 아이콘과 짧은 인라인 설명을 제공한다.
마우스 hover만 요구하지 않고 키보드 focus와 터치 tap으로도 내용을 확인할 수 있어야 한다.

- **로비 노출 리드**: 토너먼트 시작 몇 분 전부터 로비 목록에 보여 줄지 정한다.
- **등록 시작 리드**: 토너먼트 시작 몇 분 전부터 참가 신청을 받을지 정한다.
- 로비 노출 리드는 등록 시작 리드 이상이어야 한다.
- 예시: `20:00 시작 · 노출 리드 60분 · 등록 리드 20분`이면
  `19:00 로비 노출 · 19:40 등록 시작`이다.

폼은 입력값에 따른 실제 KST 노출·등록·시작 시각을 즉시 계산해 보여 준다. 반복 설정에는
첫 5회 미리보기, 전체 예정 회차 수, 마지막 회차 시작 시각을 함께 표시한다.

## 3. 인원 정책

### 3.1 저장 모델

영속 설정은 기존의 명확한 정수 계약을 유지한다.

- `minEntrants`: 2~48
- `maxEntrants`: 2~48
- `minEntrants <= maxEntrants`
- 테이블 크기: 6명 고정

`null`, 무한대, 특별 문자열을 서버나 DB에 저장하지 않는다.

- UI의 `최소 제한 없음`은 `minEntrants=2`로 정규화한다.
- UI의 `최대 제한 없음`은 `maxEntrants=48`로 정규화한다.
- UI에는 `제한 없음(현재 서비스 상한 48명)`이라고 명시한다.
- 최소와 최대가 같으면 고정 인원 토너먼트다.
- 새 토너먼트의 기본값은 최소 6명, 최대 제한 없음(48명)이다.

최소 인원은 토너먼트가 시작할 수 있는 총 필드 인원이다. 프리롤에서
`botFillToMinimum=true`이면 기존 계약대로 최소 인원까지 봇을 채울 수 있지만 휴먼이 한 명도
없으면 시작하지 않는다. wallet 토너먼트는 봇을 사용할 수 없으므로 휴먼 등록자만으로 최소
인원을 만족해야 한다. UI는 이 차이를 인원 단계에서 명시한다.

### 3.2 시작과 테이블 구성

- 예약 토너먼트는 최소 인원이 일찍 모여도 예약 시각 전에 시작하지 않는다.
- 예약 시각에 출석·경제 검증을 통과한 필드가 최소 인원 이상이면 시작한다.
- 최대 인원에 도달하면 추가 등록을 닫는다.
- 최종 필드가 2~6명이면 테이블을 하나만 만들고 처음부터 파이널 테이블 상태로 시작한다.
- 2명은 헤즈업, 3~5명은 숏핸디드 단일 테이블, 6명은 6-max 파이널 테이블이다.
- 7명 이상은 기존 멀티테이블 배치·밸런싱·브레이크·파이널 테이블 이동을 그대로 사용한다.

단일 테이블이라고 해서 예약 MTT를 자동으로 Sit & Go 시작 규칙으로 바꾸지는 않는다.
고정 좌석이 차는 즉시 시작하는 별도 Sit & Go 상품은 이번 범위에 포함하지 않는다.

## 4. 소규모 상금표

### 4.1 버전 호환

기존 회차의 정산 결과를 바꾸지 않기 위해 현재 상금표 v2를 수정하지 않는다.
새로 생성하는 토너먼트는 상금표 v3을 설정 스냅샷에 저장하고, 정산은 스냅샷의
`tableVersion`과 `presetId`를 함께 사용한다.

입상 인원과 비율은 최종 등록 마감 후 확정된 전체 참가 인원을 기준으로 한다. 레이트 레지로
필드가 커지면 최종 필드에 해당하는 밴드를 사용한다. 지급 계획은 기존과 같이 fingerprint와
함께 동결하며, 정수 반올림 잔여는 1위에 귀속해 합계가 정확히 총상금과 일치해야 한다.

### 4.2 v3 배분율

| 최종 참가 인원 | 표준형 | 넓은 입상형 | 상위 집중형 |
|---|---|---|---|
| 2명 | 100% | 100% | 100% |
| 3명 | 70% / 30% | 60% / 40% | 100% |
| 4~5명 | 65% / 35% | 60% / 40% | 75% / 25% |
| 6명 이상 | 기존 표준형 계단표 | 기존 넓은 입상형 계단표 | 기존 상위 집중형 계단표 |

공식 운영사도 참가 인원과 형식에 따라 상금 구조가 달라지고, 정확한 구조를 로비에 공개하는
방식을 사용한다. 소규모 필드에 하나의 보편적 배분표가 있는 것은 아니므로, Poker Doku는
위 세 프리셋의 성격을 유지하면서 2~5인 밴드를 명시적으로 제공한다.

## 5. 영속 스키마와 명령 계약

반복 템플릿에 다음 필드를 추가한다.

- `first_starts_at`: 운영자가 지정한 첫 회차 시작 시각
- `recurrence_ends_at`: 포함 경계인 반복 종료 시각

새 행과 활성 행에는 두 필드가 모두 필요하고 `first_starts_at <= recurrence_ends_at`이어야 한다.
마이그레이션 호환을 위해 컬럼 자체는 nullable로 추가하되, 새 생성·수정 명령과 repository
전이에서 이 활성 행 불변식을 강제한다.

마이그레이션은 기존 템플릿의 종료 시각을 임의로 추정하지 않는다. 기존 행에는 현재 생성된
회차 중 가장 이른 미래 시작 시각을 첫 시작 경계로 기록할 수 있지만
`recurrence_ends_at`은 null로 두고 모든 기존 활성 템플릿을 비활성화한다. 운영자가 종료 일시를
지정한 revision patch를 완료한 뒤에만 다시 활성화할 수 있다.

생성·수정 명령은 반복일 때 두 필드를 필수 검증한다. 단발성 토너먼트에는 두 필드를 받지 않는다.
템플릿 revision과 occurrence 유일성, owner lease, 경제 CAS 계약은 유지한다.

스케줄러는 다음 순서로 템플릿을 조정한다.

1. 템플릿의 현재 revision과 활성 상태를 읽는다.
2. 현재 비종결 occurrence와 영구 tombstone을 읽는다.
3. 첫 시작 경계와 종료 경계 안에서 다음 occurrence를 계산한다.
4. 비종결 회차가 5개가 될 때까지만 누락 회차를 멱등 생성한다.
5. 노출·등록·시작 타이머를 다시 hydration한다.

## 6. 운영 정리

이번 과다 생성 데이터는 다음 순서로 정리한다.

1. 대상 반복 템플릿을 revision CAS로 비활성화한다.
2. 해당 템플릿에서 생성된 `scheduled-hidden`, `scheduled-visible`, `registering`,
   `start-delayed` 회차를 기존 운영자 취소 경로로 하나씩 취소한다.
3. wallet 등록금 또는 프리롤 상금 예약 책임이 있으면 기존 `refund-pending` 경로를 거쳐
   실제 반환이 완료된 뒤 `cancelled`로 종결한다.
4. 취소된 회차가 공개 목록에서 사라지고 템플릿이 새 회차를 만들지 않는지 재조회한다.
5. 템플릿, 회차, 등록, 자금 원장, ops event는 삭제하지 않는다.

진행 중인 토너먼트와 완료된 과거 토너먼트는 이 일괄 정리 대상에 포함하지 않는다.

## 7. 오류 처리

- 종료 일시 누락·첫 시작보다 이른 종료: 생성/수정 거절
- 리드 순서 위반: 생성/수정 거절
- 최소·최대 범위 또는 순서 위반: 생성/수정 거절
- 5회 창 동시 조정: 기존 template revision lease와 occurrence 유일성으로 멱등 처리
- 개인 등록 회차가 일반 노출 상한 밖인 경우: 개인화 목록에 추가
- 경제 책임이 있는 회차 취소 실패: 기록을 삭제하거나 취소 완료로 위장하지 않고
  `refund-pending` 유지 및 운영 경보
- 오래된 상금표 버전: 해당 버전 계산기를 사용하며 알 수 없는 버전은 정산 중단

## 8. 검증

다음 회귀 테스트를 추가한다.

1. 시간별·일별·주별 반복이 첫 시작과 포함 종료 경계를 지킨다.
2. 긴 노출 리드와 무관하게 템플릿당 비종결 미래 회차가 5개를 넘지 않는다.
3. 완료·취소 뒤 다음 회차가 하나만 보충되고 종료 경계 뒤에는 생성되지 않는다.
4. 운영자 취소 tombstone이 재생성되지 않는다.
5. 공개 목록은 템플릿별 최대 5개이며 개인 등록 회차는 보존한다.
6. 반복 종료 필드 마이그레이션과 기존 활성 템플릿의 안전한 비활성화를 검증한다.
7. 리드 도움말과 KST 계산 예시, 반복 미리보기를 컴포넌트 테스트로 검증한다.
8. 최소 제한 없음=2, 최대 제한 없음=48, 고정 인원, 잘못된 범위를 검증한다.
9. 2~6명이 한 테이블의 파이널 상태로 시작하고 7명부터 두 테이블이 생성되는지 검증한다.
10. v2 상금표 결과가 바뀌지 않고 v3의 2~5인 세 프리셋이 정확한지 검증한다.
11. 모든 상금 밴드에서 지급 합이 총상금과 같고 내림차순인지 검증한다.
12. 취소 정리에서 등록금·프리롤 예약금이 올바른 멱등 경로로 반환되고 감사 기록이 남는지
    검증한다.

## 9. 범위 밖

- 48명을 초과하는 필드 확장
- 좌석이 차는 즉시 시작하는 별도 Sit & Go 상품
- 진행 중 또는 완료된 토너먼트의 물리 삭제
- 기존 상금표 v2 회차의 소급 변경
- 자유 형식의 운영자 정의 상금 비율
