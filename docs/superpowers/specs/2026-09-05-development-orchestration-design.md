# 남은 개발 로드맵과 모델별 오케스트레이션

2026-09-05. 사용자 지정: Astra X-High 총괄·최종 판단, Fable 5.1 기획 검토·심층 테스트, Claude Opus 또는 Astra Low/Medium 구현.

이 문서는 개발 순서와 작업 운영 방식의 제안이다. 기능별 상세 구현 계획은 해당 배치를 시작할 때 코드와 설계를 확인해 별도 파일로 작성한다. 이번 문서 작성 자체가 아래 기능의 구현·배포 완료를 의미하지 않는다.

## 1. 현재 기준과 우선순위 판단

- 코드 기준은 `cb5a619`. 포커 용어 교정·미션 전체보기·공개 MTT 숨김이 로컬 main에 반영됐고 미푸시·미배포 상태다. 마지막 확인한 운영 버전은 Fly v84(2026-09-04)다.
- Ch1~6, 가면의 공개/행동 identity 분리, 클라이맥스 CG, 영상 49클립은 이미 존재한다. 다시 신규 구현 항목으로 잡지 않는다.
- 실제 공백은 라이브 리딩 퀴즈(`pendingQuiz: null`), Ch7~12 데이터, 실패 씬 재생 연결, 스토리 XP의 일반 도장/인연 레벨 카탈로그 지급 등이다. 하드 모드는 반복 플레이 요구를 확인할 선택 항목이다.
- MTT의 디렉터·관리자 화면·wallet·영속 예약·레이트 레지는 상당 부분 구현됐다. 공개 재개는 별도의 완성도 점검 대상이다. 오래된 ‘MTT Phase 2 전체 미구현’ 목록을 구현 지시로 사용하지 않는다.
- 프로필·경제·스토리 진행은 SQLite에 저장되며 게임 방/진행 중 런은 인메모리다. ‘모든 데이터가 비영속’이라는 오래된 설명도 계획 근거에서 제외한다.
- 복구 문구 기반 프로필 복구도 이미 구현됐다(`src/server/profile-http.ts`). 신규 이메일/외부 계정 연동과 구분한다.

주요 대조 근거: `src/server/story-live-adapter.ts:361`의 퀴즈 미연결, `src/lib/story/chapters/index.ts:34`의 Ch1~6 레지스트리, `src/server/progression-service.ts:829`의 일반 카탈로그 지급 보류 설명, Ch3/Ch6 데이터에만 존재하는 `failScene`, `src/server/profile-http.ts:516`의 복구 처리. 오래된 기획의 단계 이름보다 이 코드와 최신 인계 상태를 우선한다.

## 2. 모델별 역할과 호출 원칙

| 역할 | 담당 | 맡길 일 | 책임 경계 |
|---|---|---|---|
| 총괄·최종 판단 | Astra X-High | 사용자 목적 정리, 작업 분해, 의존성·파일 소유권, 리뷰 판정, 통합·배포 판단 | 리뷰를 다수결로 처리하지 않고 근거·재현 결과로 결정 |
| 기획·경계 검토 | Fable 5.1 | 요구 누락, 잘못된 전제, 악용/경합/복구 시나리오, 구현 후 독립 심층 테스트 | 구현 담당자의 설명만으로 통과 판정하지 않음 |
| 복합 구현 | Claude Opus 또는 Astra Medium | 상태 머신·서버/클라 계약·보상 지급 등 여러 모듈이 연결되는 구현 | 정해진 작업 영역에서 구현·관련 테스트·커밋 |
| 일반 구현 | Astra Medium | UI 동작, 서버 이벤트 연결, 챕터 메커닉, 테스트 작성 | 명시된 계약 바깥의 정책 변경은 총괄에 보고 |
| 좁고 명확한 작업 | Astra Low | 승인된 대사·문구 반영, 에셋 매니페스트, 파일 목록·로그 정리 | objectives·프리셋 덱·스크립트가 들어가는 챕터 메커닉과 경제·인증·복구 정책 설계는 맡기지 않음 |

Low/Medium은 추론 노력 설정이다. 같은 Astra를 사용할 때는 모델 `gpt-6-astra`와 `low`/`medium`을 함께 명시한다. 실제 호출 가능한 다른 모델을 쓰면 모델명과 노력 설정을 모두 기록하고 ‘Astra’라고 바꿔 부르지 않는다.

기본 서브에이전트 목록에서 Fable/Opus가 지원되지 않으면 설치된 Claude Code CLI를 별도 경로로 사용한다. 현재 로컬 CLI는 `--model`, `--effort`, 읽기 전용 도구 지정과 JSON 결과 출력을 지원한다. 모델 별칭은 바뀔 수 있으므로 **결과의 실제 모델 식별자를 확인**한다. Fable 5.1을 호출하지 못하면 그 사실을 남기며 다른 모델의 리뷰를 Fable 리뷰라고 보고하지 않는다. Opus 구현도 첫 실제 배치에서 접근 가능 여부를 확인한다.

이번 역할 지정은 앞으로의 운영 규칙이다. 실행 중인 총괄 세션의 모델/노력이 자동 변경됐다는 뜻은 아니다. 실행 환경에서 Astra X-High를 선택하고, 작업 기록에도 실제 설정을 남긴다.

## 3. 배치 운영 절차

1. **Astra X-High가 작업 계약 작성**: 목표·제외 범위·기준 커밋·읽을 문서·수정 허용 파일·서버/클라 계약·수용 조건·테스트·중단 조건을 한 배치에 담는다.
2. **Fable 기획 검토**: 새 상태/경제/재접속 계약, 장기 GPU 작업, 챕터 메커닉은 구현 전에 검토한다. 단순 문구·이미 승인된 데이터 반영은 총괄이 바로 배정한다.
3. **Astra 최종 판단**: 지적별로 수용/기각/추후 검토와 근거를 기록한다. 현재 배치를 막는 문제는 계약을 고친 뒤 구현한다.
4. **구현 담당 투입**: 별도 worktree에서 한 배치씩 진행한다. 병렬 배치는 파일 소유권이 겹치지 않게 나눈다. 같은 공유 파일이 필요하면 한 배치를 먼저 통합하고 다른 배치를 갱신한다.
5. **검증과 독립 리뷰**: 동작 변경은 관련 회귀 테스트·타입·린트, UI는 브라우저 확인을 수행한다. Fable은 보상·상태 전환·복구·권한에 실패 사례를 주입해 독립 검증한다.
6. **Astra 통합**: 테스트 로그·실제 diff·재현 근거를 확인하고 worktree 커밋→main ff 병합한다. 충돌이 생기면 해결한 변경 범위에 맞춰 재검증한다.
7. **배포·피드백**: 사용자가 지시한 배포만 수행한다. Fly 단일 머신 유지, health와 해당 기능 스모크를 확인한다. 운영 반영 여부·미해결점·다음 배치를 짧게 보고한다.

검증 원칙: 로컬 HTML/고정 스냅샷, 실제 소켓 통합, 실제 브라우저 게임 플레이, 운영 스모크를 구별해 보고한다. 전체 테스트 통과만으로 모바일 체감·게임 완주를 확인했다고 쓰지 않는다. 상위 모델이라는 이유만으로 리뷰 의견이 자동 정답이 되지 않는다.

### 자원과 병렬화

- 총괄 외 동시에 실행하는 작업자는 **최대 2명**으로 시작한다. CLI의 Fable/Opus도 이 수에 포함한다.
- 기본은 구현자 1명 + 검토자 1명. 경계가 분리된 게임 구현 + 아트 작업을 병렬로 돌릴 때 검토는 완료 시점에 교대한다.
- 전체 Vitest는 의미 있는 통합 배치에서 `--maxWorkers=4`로 1회. 개별 수정은 관련 테스트를 사용한다. 같은 커밋을 각 작업자가 중복 빌드하지 않는다.
- 5090 이미지·영상 생성은 GPU 워커 1개만 소유한다. Fable/Opus/다른 에이전트가 동시에 ComfyUI에 임의 제출하지 않게 한다.
- GPU 워커 프로세스 자체는 에이전트 슬롯이 아니다. 첫 진행은 **Fable의 R1a 계약 검토 → R1a 구현자+A1 작업자 → A1 에이전트 작업을 쉬는 동안 R1a Fable 테스트** 순서다. 검토 중에도 승인된 작업 큐의 GPU 생성은 계속될 수 있다.
- 배치가 두 차례 동일 문제로 실패하거나 계약 자체를 바꿔야 하면 Astra가 범위를 재분해한다. 무한 재시도·끝없는 리뷰 순환은 만들지 않는다.

R1은 한 거대한 PR이 아니라 **R1a XP 지급**, **R1b-1 실패 씬**, **R1b-2 스파링 재도전**, **R1c 회귀 플레이 점검**으로 나눈다. R2도 공유 서버 계약→UI→Ch7 데이터/보상→심층 플레이로 쪼개되, 플레이 가능한 한 챕터가 끝나기 전 다음 막 데이터 양산을 시작하지 않는다. `views.ts`·`protocol.ts`·`story-payload.ts`·`objectives.ts`는 서버 계약 담당자 한 명이 먼저 확정하고 UI 담당자는 병합된 계약에서 출발한다. DB 마이그레이션 번호는 R1a(및 필요 시 R1b) 병합 후 R2가 할당한다.

초기 실제 동시 진행은 **R1a + A1** 두 트랙이다. R1a가 완료되면 R1b로, A1이 품질 기준에 미달하면 양산 대신 참조/포즈 설정을 조정한다. 일정은 파일럿 GPU 속도와 첫 구현 배치 처리량을 측정한 뒤 산정하며, 모델 이름만으로 일수나 장수를 약속하지 않는다.

A3는 4막 완성을 기다리지 않는다. A2와 콘텐츠 범위·인연 해금 설계가 준비되면 R2~R4 중 어느 시점에도 독립 배치로 진행할 수 있다. 추가 의상·대사 변주도 승인된 콘텐츠 규칙에 따라 작은 배치로 연결한다.

### 당장 확대하지 않는 범위

비참가자 관전·한 세션 멀티테이블·신규 이메일/외부 계정 연동·MTT 리엔트리/9-max는 별도 제품 요구가 생길 때 계획한다. 현재 6-max 게임의 수련/콘텐츠 완결성에 필요한 선행 조건으로 넣지 않는다. 인메모리 게임 방의 서버 재시작 복구와 영속 프로필 데이터도 별도 범위로 다룬다.

하드 모드는 ‘아는 내용을 수집 때문에 반복시키지 않는다’는 기존 피드백을 유지해 선택 항목으로 남긴다. Ch4~6 질문권도 R4에 묶지 않고, 코칭 수요 확인 후 별도 작은 기능으로 설계한다.

## 5. 첫 배치에서 읽을 코드와 구체적 검증

### R1a 스토리 XP 일반 도장·인연 레벨 보상

- 확인 대상: `src/server/persistence/migrations.ts:2594`의 v13 해금 뷰, `src/server/progression-service.ts:829`의 스토리 카탈로그 지급 보류 경로와 기존 일반 보상 지급 경로. 이미 구현된 v32 스토리 전용 카탈로그 보상은 유지한다.
- 계약: 기존 프로필과 신규 프로필이 같은 도장/인연 레벨에서 같은 일반 카탈로그 자격을 가진다. 여러 레벨을 건너뛰거나 히로인 여러 명에게 XP를 받은 보상도 누락되지 않고, 완료 이벤트 재전송·재시작·소급 확인은 중복 지급하지 않는다.
- 소급은 첫 히로인만 담긴 과거 summary만 재생하지 않는다. 서버 정본의 도장 레벨·모든 히로인 인연 레벨과 실제 보유 아이템의 차이로 누락 후보를 구한다. 과거 이벤트 JSON을 고쳐 쓰지 않고 멱등 보정 지급과 검증 가능한 근거를 새로 남긴다. 근거 뷰·트리거를 무력화하거나 임의 이벤트 전체를 허용하지 않는다.
- Fable 반증 사례: 일반 XP만/스토리 XP만/혼합 XP, 레벨 경계 직전→직후/한 번에 여러 레벨, 기존 보유 아이템, 같은 완료 두 번, 이전 DB 업그레이드, 백필 도중 중단. 첫 완주·S 향상·exam·재도전·데일리 보상을 교차해 별도 보상 경로의 중복도 확인한다.
- 산출물: 지급 단일 소스와 필요 시 마이그레이션 설계, 회귀 테스트, 기존 유저 소급 전략. 기존 컬렉션 화면과 인벤토리로 결과를 확인하며 새 관리 화면은 만들지 않는다. 실제 경로 조사 후 변경 파일·SQL·테스트를 세부 계획에 고정한다.

### R1b 실패 씬과 재도전

- 확인 대상: `src/server/story-run-coordinator.ts`, `src/lib/story/types.ts`, Ch3/Ch6의 `failScene`, StoryStage의 화면 단계와 기존 재도전 이벤트.
- 현재 [다시 도전]은 챕터 전체 재시작이다. 이것을 새 기능의 완료 근거로 쓰지 않는다.
- R1b-1 계약: Ch3/Ch6 미통과 시 **서버가 실패 전용 씬 단계를 소유**하고, failScene 재생/스킵 후 결산으로 이동한다. 씬을 보는 동안 런을 먼저 삭제하지 않아 일반 연결 끊김 뒤 현재 씬으로 돌아올 수 있게 한다. `failScene`이 없는 챕터는 기존 결산을 유지한다. 성공 보상·이전 완료 기록을 잘못 변경하지 않는다.
- R1b-2 계약: 결산의 [스파링만 재도전]은 실패 결과에 묶인 서버 검증 재도전 정보로만 실행한다. 본인 프로필·챕터·완료 드릴·실패 스파링을 서버가 검증하고, 이미 푼 씬/레슨/드릴을 반복시키지 않는다. 클라이언트가 임의 스텝이나 점수를 지정하지 못하며 새로운 스파링 시도의 미션/스택은 초기화한다. 재도전 정보의 만료/서버 재시작 시에는 이용 불가 안내와 기존 전체 재시작 경로를 제공한다. 보존 시간·재접속·소비 방식은 구현 전 세부 상태 계약에서 함께 고정한다.
- Fable 반증 사례: 실패 직후 disconnect, 씬 진행 중 재전송, 재도전 연타, 실패/성공 반복, 이전 보상 보유, 서버 재시작 후 재입장.

### A1/A2 로컬 제작 기반

- 상세 제작 기준: `docs/superpowers/specs/2026-09-05-art-library-production-design.md`.
- 기존 실행 참고: `scripts/art/story-video.md`, `scripts/art/story-video-h3.py`; 새 후보는 로컬 제작 폴더에 보관하고 기존 원본을 교체하지 않는다.
- Fable은 제작 상태·복구 계약과 명세 누락을 검토한다. 얼굴 일관성·그림 매력·연출의 최종 채택은 시각 검수와 사용자 피드백으로 결정한다.

### R1c 기존 1·2막 심층 플레이

- 실제 라이브 액션 중 끊김→grace 만료→room-lost→이어하기에서 스택·미션·프리셋 진행·identity를 확인한다. 서버 재시작의 인메모리 런 소멸과 저장된 완료 기록은 구별한다.
- 모바일 화면과 가능한 실기기에서 미션 모달 중 턴 만료, 앱 백그라운드 복귀, 입력 잠금 해제, 영상 자동재생 차단·크롭·reduced-motion, 보상 이후 인연씬 큐를 확인한다.
- 2막 3챕터 완주에 따른 파란띠 승급을 확인한다. 자동화가 검증할 수 없는 실제 소리·기기 동작은 사용자 확인 항목으로 남긴다.

### R2 퀴즈 우회 방지와 챕터 공개

- Ch7 필수 가면 퀴즈는 4문 제시·3문 정답을 요구한다. 출제 수를 분모로 삼고 사용자 미응답/서버 deadline 만료는 오답 처리한다. 답변 1개만 맞히기·전부 무응답으로 통과할 수 없다. 재접속은 동일 quiz ID와 deadline을 사용한다.
- 서버 문제로 필수 문항을 제시하지 못하면 완료를 인정하지 않고 복구/재시도 가능한 미완료 상태로 둔다. 다른 행동 목표의 ‘기회 없음’ 예외를 전역적으로 없애지 않고 필수 퀴즈의 최소 제시/완료 조건을 별도로 적용한다.
- 보상은 `src/lib/story/rewards/catalog.ts`와 DB `story_reward_catalog`의 패리티를 함께 검증한다. 허브 3막 노출·Ch7 해금·막 완주 판정도 포함한다. Ch7만 배포된 동안 Ch7 하나가 3막 전체 완료로 판정되어 갈색띠를 주면 안 된다.
