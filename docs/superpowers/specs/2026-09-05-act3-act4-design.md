# R3/R4 수련 확장 설계 — 총괄 확정

승인된 12챕터 명세를 Ch7 이후까지 완성한다. 기존 엔진의 서버 권위·CSPRNG·홀카드 비공개·팟 회계·좌석 순서 계약은 유지한다. 실제 Fable 5.1 xhigh의 읽기 전용 코드 검토를 거쳐 총괄이 확정했다. 원문은 `../reviews/2026-09-05-r3-r4-design-fable.md`, 구현 시 아래와 마지막 확정 계약을 함께 따른다.

## 순서와 공통 계약

- R3 = Ch8~9 + combos/hand-reading/nuts + 라이브 리딩 퀴즈 + 3막 보상. R4 = Ch10~12 + MDF/SnG 문항 + 종합 체크리스트 + 실제 졸업 SnG/검은띠 재도전.
- 3막 세 챕터는 2막 전체 완료 후 비선형, 4막 세 챕터는 3막 전체 완료 후 비선형이다. R2의 고정 4막×3 커리큘럼을 사용한다.
- 장면·레슨·드릴·실제 프리셋 연습·랜덤 스파링·실패 씬·에필로그·결산을 모두 작성한다. 기존 대사/리액션 문체와 포커 용어 규칙을 적용한다. 비선형 순서를 가정해 아직 받지 않은 띠를 대사로 수여하지 않는다.
- 새 카탈로그는 TS와 다음 DB 마이그레이션에 같은 데이터로 추가한다. R2 v35 이후 R3 v36, R4 v37부터 순차 사용하며 이미 적용된 마이그레이션은 수정하지 않는다.
- 실제 파일 없는 신규 CG를 AVAILABLE로 등록하지 않는다. 기존 ScenePlayer의 캐릭터/배경 폴백은 유지하고 아트 공급은 별도 검수 뒤 연결한다.
- 하드 모드·질문권·MTT 공개 복구는 이 배치에 넣지 않는다.

## 드릴 생성과 포커 설명

모든 생성기는 기존 seed/32회 리롤/서버 채점/클라이언트 정답 제거/복습 노트 규약을 공유한다. 숫자와 해설 facts는 같은 계산 결과에서 만든다. 문제 상황에 없는 블라인드·콜 가격·레인지를 몰래 가정하지 않는다.

- **콤보**: 포켓 페어 6, 수딧 4, 오프수트 12를 출발점으로 실제 `rangeCombos`와 알려진 카드 제거를 사용한다. Ch8은 블로커 1개, Ch9는 2개와 페어 보드를 포함한다. 중복 레인지 토큰은 중복 집계하지 않고 차단 카드/비어 있는 레인지도 테스트한다.
- **넛츠**: `findNuts`/`evaluateHand`를 사용한다. 현재 보드에서 가능한 최고 핸드를 묻고 후보 중 동일 최고값이 여럿이면 단일 선택 문제는 리롤한다. 보드 자체가 넛츠인 경우, 플러시/스트레이트/풀하우스와 블로커를 검증한다. 히어로의 알려진 카드로 불가능한 상대 조합을 제외한다.
- **핸드 리딩**: 임의로 봇의 실제 홀카드를 알아맞히게 하지 않는다. 공개 액션과 **문제에 명시된 상대 레인지/액션 가정**을 기반으로 제거되는 콤보·남는 밸류/블러프·블로커 영향을 묻는다. 레인지 추정은 가정임을 해설과 문항에 밝힌다. 사실처럼 '체크레이즈는 언제나 세트'라고 가르치지 않는다.
- **MDF**: 벳 전 팟 P, 상대 베팅 B에 대해 P/(P+B). 0에퀴티 블러프의 자동 수익을 막는 레인지 전체의 기준이라는 한계를 설명한다. 특정 핸드의 의무 콜이나 실제 상대에 대한 절대 법칙으로 쓰지 않는다. 콜 필요 에퀴티 B/(P+2B)와 혼동하지 않도록 숫자/용어를 구분한다.
- **SnG**: 스택/BB, 앤티가 명시된 경우 M, 프리즈아웃·상금권·블라인드 인상·쇼트스택 판단. 푸시/폴드는 포지션/유효스택/앞 액션/상대 콜 가정이 명시된 수기 문항으로 제한한다. 현재 캐시용 프리플랍 임계를 무조건 SnG 푸시 차트로 재사용하지 않는다.
- 신규 템플릿은 실제 registry/해설/일일 해금/드릴 통계/검증기에서 연결한다. 존재만 하는 ID나 플레이 불가능한 슬롯은 허용하지 않는다.

## R3: 리딩 퀴즈와 행동 목표

### 공개 사실 기반 라이브 퀴즈

Ch8의 리딩 퀴즈는 실제 히어로 리버 결정 **직전**, 공개 보드·히어로 핸드·현재 가격으로 만든 제한된 문제다. 상대의 실제 홀카드/내부 decision reason은 입력에 사용하지 않는다. 질문은 '이 추정 레인지대로라면 내 콜이 유리한가' 또는 '블로커를 빼면 내가 이기는 콤보가 몇 개인가'처럼 명시된 레인지 가정에 대한 계산으로 정답이 유일해야 한다. 모호한 가격 경계 ±5%p/멀티웨이/사이드팟은 출제하지 않는다. 최대 2문항, 같은 핸드·액션에는 1회만 출제한다.

이 방식은 전 핸드 결과를 이미 본 뒤 정답을 맞히는 누출을 피한다. 실제 정답을 보여주기 전에 답을 잠그며, 공개된 상대 성향의 보조 정보만 허용한다. 봇의 진짜 홀카드나 속마음을 정답 근거로 전송하지 않는다.

- RoomManager에 스토리 전용 `beforeHeroTurn` 선택 훅을 추가한다. `startPlayerLoop`가 휴먼 기본 타이머를 만들기 전 호출하며 퀴즈 hold인 경우 해당 턴 타이머를 시작하지 않는다. 일반 캐시/SnG/MTT 경로는 영향받지 않는다.
- hold 중 서버는 player-action/timebank를 거절한다. 버튼을 UI에서 숨기는 것만으로 보호하지 않는다. 중복 startPlayerLoop·소켓 resync가 질문/deadline을 다시 만들지 않는다.
- opaque quizId + roomId/handNumber/actionSeq의 서버 스냅샷 키를 보존한다. R2의 안전한 story-quiz ACK/소유권/중복 receipt를 재사용하되 가면의 4문항 일괄 공개와 별개 모드로 관리한다.
- 30초 deadline은 서버 소유. 응답/시간 만료 뒤 해설을 표시하고 [계속하기]로 같은 히어로 턴을 시작한다. 해설 확인은 최대10초이며 그 뒤 정상 포커 턴 타이머를 시작한다. 퀴즈 응답만으로 포커 액션을 자동 실행하지 않는다.
- 연결이 끊기면 **기존 RoomManager의 즉시 자동 체크/폴드를 유지한다**. 원래 턴의 키가 바뀐 미응답 질문은 invalidated로 기록해 오답 분모에서 빼고 다음 기본 턴/핸드 경계의 기존 부재 처리로 이행한다. grace 만료/방 소멸도 미응답을 무효화한다. 해당 원본 핸드를 새 방에서 계속한 것처럼 표시하지 않으며 이미 답한 점수는 보존한다. 이는 Ch7의 핸드 사이 가면 퀴즈와 다르다. Ch7의 오프라인 절대 deadline 계약은 변경하지 않는다.
- 리딩 점수 = 유효하게 답이 확정된 문제 중 정답 비율 ≥50%. 실제 출제 기회가 없으면 판정 불가(null)이며 기존 조건부 목표 규약대로 제외한다. Ch7 필수 4문항 규약을 이 선택적 기회형 퀴즈에 적용하지 않는다.

### 챕터 구성

| 챕터 | 구성 | 통과와 보상 |
|---|---|---|
| Ch8 클로이 | ODDS2/COMBO2/CALL3, 구미 리버 콜·초코 리버 폴드 프리셋, 구미/초코/비비안 12핸드 | 구미 상대 합리적 가격의 리버 탑페어+ 콜(목표2), 초코 상대 원페어 과도 콜≤1, 리딩퀴즈≥50%. 도장250·클로이100 |
| Ch9 엘레나 | READ3/COMBO2/NUTS2/ACT1, 루나 체크레이즈·사쿠라 리레이즈 폴드 프리셋, 루나 보스 3인15핸드 | 약한 원페어로 루나 체크레이즈를 맞은 기회의 폴드≥70%, 과도콜≤2. 도장300·엘레나100·3막전체완료갈색띠 |

숫자 '2회 콜'은 카드 운 때문에 기회 1회 중 옳게 1회 콜하고도 실패시키지 않는다. 출제 기회보다 높은 횟수 목표는 실제 기회 수까지 한정하며, 2회 달성은 조기 종료 기준이다. 기회0은 null. 강한 풀하우스/넛츠까지 무조건 폴드를 요구하지 않으며 보드만 만든 페어·투페어를 히어로의 탑페어+로 세지 않는다. 라이브 기회 평가와 드릴 해설은 동일한 순수 정책을 사용한다.

## R4: Ch10~11

- **Ch10**: BE2/MDF2/CALL2/ACT2, 트리플 배럴 콜다운·오버벳 폴드 프리셋, 잉그리드/드라코12핸드 뒤 비비안 HU20핸드. 탑페어+ 적정 가격 콜다운 목표2(기회 한정), 에어 리레이즈0, 오버벳 결정 정답비율≥50%. 드로우/메이드/보드만 강한 경우를 구별하고 고강도 플레이를 무조건 콜하도록 하지 않는다. 도장300·비비안100.
- **Ch11**: 복습 노트가 있으면 그 유형을 우선하되 같은 문제의 암기 반복을 막는 새로운 seed로 종합8문. 파트너 담당, 하나 리뷰. 히어로+히로인5명, 중복 아바타 없이 6인30핸드. 하위 레인지 참여0/림프0/c벳≥2/3/밸류≥2/3/오즈 위반≤2 중 **3개**를 달성하면 통과. `any-k-of` 정책을 순수함수로 정의하며 null을 자동 성공 1점으로 세지 않는다. 분모가 부족하면 3개 이상 평가 가능한 체크리스트를 구성하거나, 기회형 제외 후 남은 평가항목 중 3개까지로 요구량을 한정한다. 원래 드릴 완료 게이트는 유지한다. 도장350·파트너100·하나20(파트너가 하나면 합산120).
- 실패 checkpoint는 해당 실패 라이브 스텝 직전까지만 보존한다. Ch10 첫 스파링을 통과하고 HU에서 실패하면 HU만 재도전한다. Ch8은 새 라이브 시도에서 새 리딩 기회를 평가한다. 기존 R1 재도전의 새 run/방/스택/중복보상 방지 계약을 사용한다.

## R4: Ch12 졸업 SnG

### 실제 게임과 종료

- 드릴 SNG6+종합2, 8BB 푸시 프리셋 이후 **실제 engine gameMode:'sng'**인 스토리 전용 연습경제 6인. 시작1,000칩·레벨2분·일반 SnG 스케줄을 기반으로 하는 서버 전용 구조. 첫 핸드6,000칩, 현금 지급/에스크로/리바이/파산리필 없음.
- 일반 SnG의1,500칩/3분 동작은 유지한다. 서버 소유 room 옵션의 스토리 구조 ID로 선택하며 외부 create-room payload로 임의 블라인드 구조를 주입하지 못한다. 룸매니저의 첫 레벨/deadline/다음레벨/공지와 엔진 시작 스택이 같은 구조를 쓴다.
- 실제 엔진의 hero 결과 place가 확정되면 완료한다. 히어로 탈락을 보려고 나머지 봇들의 우승까지 기다리지 않는다. 히어로 우승은 tournament.finished와 place1로 확정한다. maxHands/파산을 일반 스파링 실패로 처리하지 않는다.
- 최종 순위는 동시 탈락 시 handStartChips 계약을 따른다. 어댑터가 chips만 보고 순위를 다시 추정하지 않는다. 결과 DTO에 server-confirmed place/entrants를 전달한다.
- 연결 끊김/자리비움은 정규 SnG처럼 딜인·블라인드·자동 액션 유지한다. Ch12에 캐시형 grace회수/봇파산리필/timeout hold/방 재생성 스택 초기화를 적용하지 않는다. 재접속은 같은 방·스택·순위. 사용자가 명시적으로 수련을 포기하면 그 실행을 취소하고 연습 방을 정리한다(완주 보상 없음).
- 서버 재시작은 현재 인메모리 런 계약대로 종료한다. 수련 SnG를 이어지는 척 복원하지 않는다. 영속 프로필 보상/확정 졸업 기록은 유지한다.
- 기본 목표25분은 실측 예산이며 강제 우승/시간만료 임의순위로 달성시키지 않는다. 단축 타이머 테스트와 기본시간 봇 시뮬레이션으로 실제 진행/상한 구간을 보고한다.

### 완료·검은띠·재도전

- Ch12는 탈락 포함 실제 SnG 순위 확정으로 챕터 통과/첫 도장500·전원 인연30. 3위 이내에만 검은띠 자격, 1위에만 사범대리 칭호. 검은띠 표시 자체는 **4막 전체 완료 + ITM자격**의 교집합이다.
- Ch12에는 드릴만으로 졸업하는 실력 확인 버튼을 제공하지 않고 서버도 exam 모드를 거절한다. 다른11챕터의 실력확인은 유지한다.
- Ch12 완료 프로필은 허브/결산에서 [졸업 대결만 재도전]을 항상 선택할 수 있다. 기존10분 실패 checkpoint가 만료돼도 durable completion으로 자격을 확인한다. 신규 모드 `graduation`은 Ch12에서만 허용하며 활성 런/어댑터 충돌을 거절한다.
- graduation 모드는 새 run/방/1,000칩으로 SnG만 시작한다. 드릴 점수를 과거 결과에서 복제하거나 가상의8문 만점으로 표시하지 않는다. 결과에는 순위와 새로 얻은 졸업자격/칭호를 보여준다. 첫 XP·리플레이 XP·전원 인연·첫완주칩/S칩은 모두0이다. 스토리 SnG는 일반 SnG 순위 XP/스트릭/미션 경로를 차단하고 일반 핸드 XP 캡처도 생략한다. 일반 cash/SnG 진행 보상은 유지한다.
- 확정 졸업 기록을 profile/runId unique receipt와 입력 fingerprint로 저장한다(실제 place/entrants, mode, 시간). flag:black/우승 플래그는 이 receipt와 같은 DB 트랜잭션에서 단조롭게 갱신한다. 동일 run 결과 재전달은 멱등, 같은 run 다른 순위는 오류다. 클라이언트 제출값으로 순위를 받지 않는다. full모드 첫 보상과 graduation-only 보상 차이를 서비스/리포지토리 테스트로 고정한다.
- 보상 트랜잭션 실패 시 실제 결과를 유지한 채 재시도한다. 영속화에 실패했는데 UI만 검은띠를 수여하거나 결과를 버리지 않는다. 카탈로그 reconcile은 확정된 플래그에서 멱등 지급한다.
- 파트너6명별 졸업 VN은 소유한 파트너로 분기한다. 순위가4~6위면 격려·다음도전, ITM이면자격안내, 우승이면우승대사. 아직 4막 전체를 완료하지 않았다면 검은띠를 이미 받은 것처럼 말하지 않는다.

## Fable 검토 후 총괄 확정 계약

### R3: 턴 퀴즈와 평가

1. `beforeHeroTurn`은 실제 활성 휴먼이며 자동액션 대상이 아닐 때만 호출한다. `(roomId, handNumber, actionSeq)`가 같으면 재발급하지 않는다. `processPlayerAction`과 `useTimeBank`도 RoomManager에서 같은 turn-hold 가드를 검사한다. 소켓만 막는 구현은 불충분하다.
2. RoomManager의 기존 `resumeRoom`은 새 핸드 시작용이다. 진행 중 히어로 턴 재개는 스토리 전용 `resumeHeroTurn`으로 `startPlayerLoop`→`onUpdate` 순서를 보장한다. 어댑터에 별도 `turnHold`와 질문/해설 타이머를 두며 기존 핸드 경계 `session.hold`/유휴 sweep과 섞지 않는다. `onHandComplete`, 턴 키 변경, drop/forceFinish/shutdown에서 모두 정리한다. UI의 hold 표현과 서버 핸드 경계 hold 판정도 구별한다.
3. `HandReadQuizView`의 4문 리터럴을 일반 문항수 타입으로 확장하되 Ch7은 실제값4와 기존 일괄공개 정책을 유지한다. `answerQuiz`, `resume`, `objectiveViews`에 reading 정책 디스패치를 넣는다. 퀴즈는 공용 body-portal Modal로 표시해 R2에서 발견된 작은 화면 가림/초점 탈출을 반복하지 않는다.
4. 에퀴티는 명시적으로 보여준 레인지에서 알려진 히어로/보드를 제거한 콤보를 전수 평가한다. 10콤보 미만, 멀티웨이, 올인/사이드팟, 필요 승률과 ±5%p 이내면 미출제. 팟은 공개 총기여, 콜은 currentBet−heroBet로 계산하고 유효 콜 스택 제한을 확인한다. 실제 상대 홀카드·이후 액션·승패를 바꿔도 질문/평가는 같아야 한다.
5. 새 횟수 목표에는 명시적인 최종 기회 캡 옵션을 둔다. `ObjectiveExtras.final`은 최종 summary에서만 true이고 조기 종료는 false다. 최종 target=min(설정횟수,실제기회),0기회=null. 기존 Ch1~7 목표를 일괄 완화하지 않는다. 비율과 횟수를 둘 다 설정하면 한쪽을 조용히 무시하지 않도록 검증/판정을 정의한다.
6. Fable의 Ch9 `target:1`만 추가하면 전부 프리플랍 폴드가 막힌다는 주장은 수용하지 않는다. 기회0이 null이면 target도 그 우회를 막지 못한다. 기존 기회형 평가의0기회 제외 계약을 유지하고, 필수 드릴·프리셋을 포함한 전체 수련 완료와 실전 미측정을 정확히 표시한다. 카드 운 때문에 불가능한 실행을 강요하지 않는다. 루나 체크레이즈는 공개 액션 replay에서 상대 체크→히어로 벳→상대 레이즈의 동일 스트리트 사실로 만들고, 강한 메이드/보드만 강한 경우를 구별한다.
7. Ch9 신규 씬은 `2026-09-05-art-first-supply.md`의 실제 배치된 엘레나4개 CG를 사용한다. 아트 담당자는 ID/챕터 매핑을 소유하고 챕터 구현자가 scene 라인을 소유한다.

### R4: 체크리스트와 졸업

1. Ch11은30핸드 고정, 조기 종료 없음. 체크리스트 `any-k(3)`는 null 제외 후 `min(3,판정가능항목수)`를 요구한다. 추가 실행 확인을 명시적으로 화면에 표시한다: 실제로 주어진 적정 오픈/올바른 c벳/밸류 기회 중 적어도1회 실행. 오픈 기회는 액션 이전 핸드·포지션·언오픈 팟으로 판정하므로 모두 폴드해서 c벳/밸류 기회를0으로 만드는 우회를 막는다. 세 실행 기회 모두 실제0이면 이 확인만 미측정 제외한다. Fable의 'c벳·밸류 모두0이면 minExecuted를0으로 낮추면 폴드-전부가 막힌다'는 부분은 자기 모순이라 채택하지 않았다. 판정가능한 오픈 기회를 계속 폴드한 사례/실제0기회 사례를 각각 테스트한다.
2. Ch12는 새 step kind 대신 sparring의 `LiveTableSpec.tournament` 정책을 쓴다. 서버 전용 `sngStructureId`→`resolveSngStructure`가 levelMs/levels/startingStack을 일관되게 제공한다. 표준은 기존1,500/3분, graduation은1,000/2분. 시작공지·levelIndexAt·타이머·첫/다음핸드가 같은 구조를 쓴다. 외부 room payload는 필드를 거절한다. Ch12 turnTime30초·botThinkScale0.5를 기본으로 한다.
3. 이 정책에서 beforeHand의 캐시 timeout/disconnected hold와 일반 파산 실패를 우회한다. 기존 SnG 부재딜인/자동액션을 유지하되 스토리 SnG의 [게임 복귀] 요청은 `toggleSitOut`에서 허용한다(스토리의 임의 자리비움 버튼을 새로 허용하지 않는다). `fillWithBots`는 스토리 방을 거절한다. 서버 room-lost는 시작 전만 재생성할 수 있고 첫 핸드 이후에는 결과 없는 종료이며 새 스택으로 이어가지 않는다.
4. `completeProgressionTournament`는 스토리 방을 제외하고 어댑터 `skipHandProgression`도 graduation 정책에서 true다. 우승 때만 일반 SnG XP가 지급되는 비대칭을 차단한다. 히어로 finishPlace 또는 실제 tournament.finished로만 순위를 확정한다. maxHands는 매우 큰 폭주 가드로서 운영 오류 종료만 하며 임의 순위/성공을 만들지 않는다.
5. `onStepFinished` 뒤 코디네이터가 에필로그로 넘어가기 **전** 졸업 receipt와 단조로운 ITM/우승 자격 플래그를 같은 DB 트랜잭션으로 기록한다. `(profileId,runId)` unique와 place/entrants/mode/안정된시각의 fingerprint를 검증한다. 실패하면 pendingGraduation과 같은 결과를 유지하고 advance/resend에서 재시도한다. 입력이 바뀐 중복 결과는 거절한다. 인메모리 런 소실과 이미 영속된 자격은 구분한다.
6. full Ch12 결산의 완료 기록과 첫 XP/인연 지급도 동일 DB 트랜잭션에서 확정한다. `recordCompletion`만 성공하고 XP 실패 뒤 재시도가 replay로 바뀌는 손실을 허용하지 않는다. catalog 지급은 확정 receipt/완료 조건에서 멱등 reconcile한다. 실패 동안 완료/보상을 UI에 확정 표시하지 않는다.
7. `graduation` 모드는 durable Ch12 완료자만 허용하고 SnG→파트너 에필로그→결산만 실행한다. drill DTO는 null, 완료횟수/최고등급은 변경하지 않고 XP·인연·칩 반복 지급은0이다. 새 자격/칭호만 멱등 지급한다. Fable의 replay XP 지급 제안은 승인된 반복0 계약과 달라 채택하지 않는다.
8. 검은띠 카탈로그는 새 graduation entitlement(모든필수막완료+ITM플래그)와 `deriveBelt`가 같은 순수 판정을 공유한다. 플래그 하나만으로 검은띠를 지급하지 않는다. `run.beltAtStart`로 이후 receipt 선기록 때문에 승급 연출이 누락되지 않게 한다. `Chapter.examDisabled`를 Ch12에 두어 허브와 서버가 동일하게 거절한다.

기획 검토로 필요하다고 확인된 수명주기 수정은 승인된 구현 범위 안에서 진행한다. 새로운 사용자 승인 단계는 추가하지 않는다. R3를 먼저 구현·검증하고 R4는 그 코드 위에서 별도 실행 계획을 작성한다.
